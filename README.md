# reply-funnel-sql

A small SQL project analyzing a cold email outreach funnel: who replies, and whether follow-up emails are worth sending. All data is synthetic and generated by code in this repo.

```bash
python3 run.py                        # builds the database, writes the report
python3 -m unittest test_recovery -v  # checks the analysis against known answers
```

No installs, no Docker, no database server. `sqlite3` ships with Python.

**Findings:** [reports/report.md](reports/report.md)

---

## Why synthetic data

I did cold email outreach as a Data Analyst Intern at GAO Tek — building lead lists, running them through Apollo and Mailmeteor, tracking opens and replies. Two questions came up that I never got to answer properly: does contact seniority actually affect reply rate, and does a longer follow-up sequence help or just annoy people.

I can't publish that data. It's a client's confidential business information, and it isn't mine to hand out. So I wrote a generator that produces data with the same shape and analyzed that instead. Nothing in this repo touches a real campaign.

That decision creates an obvious problem, and it turned out to be the interesting part of the project.

## How do you know the SQL is right?

If I make up the data *and* write the queries, I could easily produce a confident-looking report built on a broken query. Nobody could tell, including me.

So I split the project in two.

`effects.py` is the answer key. It holds two effects and nothing else:

1. **Seniority** — decision-makers reply about 3× as often as individual contributors, per email opened.
2. **Follow-up fatigue** — each additional touch in a sequence replies worse than the one before, down to about 14% of the touch-1 rate by touch 5.

`generate.py` reads that file and builds the database from it, at a fixed seed, so every run produces identical data.

**The SQL never reads `effects.py`.** The three queries in `sql/` know nothing about what was planted. Then `test_recovery.py` runs those real queries and asserts the numbers recover both effects on their own.

That's the whole argument: I know the effects are real because I put them there, and I check that the queries find them without being told what to look for.

### Measuring per open, not per send

The seniority effect is planted on replies *given an open*, and the query measures it that way. If I measured replies per send instead, any difference in how often each group opens email would show up as a seniority effect — which would be the wrong conclusion from the right number.

To keep that clean, the generator gives both groups an identical 34% open rate. Seniority moves replies and nothing else, so there's exactly one explanation for a gap in the reply numbers.

### Proving the test can fail

A test that can't fail proves nothing, so I checked mine in a scratch copy of the project, twice.

**Flattening both effects** — setting the seniority multiplier to 1.0 and every touch multiplier to 1.0 — failed two tests:

```
AssertionError: 5.95 not greater than 6.08 :
  decision-makers should reply more per open; got dm=5.95%, ic=6.08%

AssertionError: reply rate per open should fall at every touch;
  got [5.86, 5.84, 6.37, 6.45, 5.95]
```

Worth being precise about what happened: the two *magnitude* tests still passed. They compare the recovered ratio against whatever `effects.py` says, and with a flat answer key a flat result is the correct answer. It's the direction and ordering assertions that catch a missing effect.

So I ran a second mutation that's closer to the real risk — leaving the effects intact and breaking the query instead, swapping `SUM(s.replied)` for `COUNT(s.replied)` so it counts rows rather than summing the reply flag:

```
AssertionError: 0.995 != 3.0 within 0.9 delta :
  planted 3.00x, recovered 1.00x (dm 293.55% on 1742 replies, ic 295.0% on 895 replies)
```

That's the failure that matters. A broken query gets caught, and the message says what was planted and what came back.

## What the analysis found

From the committed report, on 115,271 synthetic sends:

| | |
|---|---|
| Opened | 39,152 (33.97% of sends) |
| Replied | 2,637 (2.29% of sends, 6.74% of opens) |

**Seniority.** Decision-makers replied to 11.14% of what they opened against 3.81% for individual contributors — **2.92× more often**, on 1,742 and 895 replies. Planted at 3.0×.

**Follow-up fatigue.** Touch 1 replies at 10.66% per open, falling monotonically to 1.46% by touch 5 — an **86% drop**.

| touch | sends | replies | reply rate per open |
|---|---|---|---|
| 1 | 40,000 | 1,446 | 10.66% |
| 2 | 32,844 | 704 | 6.24% |
| 3 | 23,261 | 326 | 4.18% |
| 4 | 13,592 | 134 | 2.89% |
| 5 | 5,574 | 27 | 1.46% |

Every sentence in the report is computed from the query results and a stated threshold — a cell needs at least 25 replies before the report describes it in words. No interpretation is typed by hand, so the prose can't claim an effect the data doesn't show. Touch 5 clears that bar by two replies, which is thinner than I'd like.

## How I used AI

I designed this and used Claude Code to build it.

Mine: the two effects and why they're the ones worth planting, measuring replies per open rather than per send, keeping the answer key out of the SQL, and the choice of SQLite so the whole thing runs with no setup. The scope is deliberately small — I wanted a project I can fully explain in an interview, not a tour of SQL features.

Claude's: the generator, the queries, the report renderer, and the tests, written from that design. It also caught something I'd have missed — my first dataset left touch 5 with only 4 replies, too thin to assert anything about, so the data was scaled up until the smallest cell carried real weight.

The mutation testing above was run at my instruction and I've reproduced both failures myself. I wanted the "can this test fail" question answered with output, not assurance.

## Files

|---|---|

| `generate.py` | Builds `funnel.db` from the answer key, seeded. |
| `sql/schema.sql` | Three tables: companies, contacts, sends. |

The database is gitignored — it's rebuilt by `run.py` in under a second.

## What I'd add next

- **Confidence intervals.** The report says 2.92× but not how precise that is. Touch 5 rests on 27 replies and the report treats it the same as touch 1's 1,446. A Wilson interval per cell would make the thin cells visibly thin.
- **A third effect worth arguing about.** Both planted effects are ones I already believed. A more honest test of the method would be planting something I'd expect to be wrong — say, that industry doesn't matter — and seeing whether the analysis correctly finds nothing.

## Known limitations

- Every result depends on effects I chose. This validates that the SQL recovers what's in the data; it says nothing about whether real outreach behaves this way.
- Tolerances in the recovery test are ±30%, wide enough to absorb sampling noise. A subtle magnitude bug inside that band would pass — the ordering assertions are the tighter check.
- One seed. The tests pass deterministically at seed 20260904 and I haven't checked them across a range of seeds.
- No statistical significance testing anywhere. Differences are reported as observed, with a sample-size threshold as the only guard.
